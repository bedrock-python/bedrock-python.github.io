# Практикум: код из статьи о Domain-Driven Design {#lab-the-code-from-the-domain-driven-design-article}

Запускаемые проверки к [статье](../../posts/2026-11-02-domain-driven-design.md).
Нужен работающий Docker. Скрипт создаёт и удаляет собственный контейнер PostgreSQL;
существующие базы не используются. Выполните команду из
`docs/blog/lab/2026-11-02-domain-driven-design` в клоне репозитория:

```bash
uv run --no-project --python 3.13 --with-requirements requirements.txt ddd_lab.py
```

В `requirements.txt` закреплены sqlalchemy-foundation-kit 0.5.1, omni-box 0.3.1,
SQLAlchemy 2.1.6, asyncpg 0.32.0 и testcontainers 4.15.0. Образ `postgres:17-alpine`;
скрипт печатает версию сервера (в проверенном запуске 17.11).
sqlalchemy-foundation-kit 0.5.1 стал первым релизом, который импортируется на SQLAlchemy 2.1
([#78](https://github.com/bedrock-python/sqlalchemy-foundation-kit/issues/78), баг нашёлся при подготовке этого практикума).

Своей копии кода из статьи у практикума нет. `ddd_lab.py` читает блоки кода из английской
и русской редакций, проверяет, что в обеих один и тот же код, и запускает каждый блок в чистом
пространстве имён с теми именами, которые блок считает известными. В `support.py` лежит то,
что статья опускает: таблицы, репозитории и полный `User` с CanExecute / Execute и доменными событиями.

В памяти проверяется, что:

- анемичный `PersonService` оставляет `is_employee` устаревшим, как и сказано в статье;
- одиннадцатый заказ делает `Customer` клиентом Advanced, а заказы доступны только на чтение;
- `OverbookingPolicy` принимает 110% вместимости и отказывает на 111%;
- функциональное ядро возвращает `FileUpdate`, оболочка его применяет, а тест из статьи проходит без диска;
- каждый из трёх вариантов трилеммы отклоняет занятый адрес;
- в CanExecute / Execute контроллер сначала спрашивает домен, а вызов `change_email` в обход проверки падает (в блоке нет `assert`);
- `Money` равны по значению и проверяют валюту и знак; `Order` равны по id и остаются хешируемыми;
- `transfer`, `DelinquentInvoice` и обёртка `MessageBus` ведут себя так, как описано.

На PostgreSQL скрипт добавляет уникальное ограничение тем же `ALTER TABLE`, что и в статье, и запускает собранную `change_email`:

- пользователь, компания и строка outbox коммитятся вместе, а у события `aggregate_type="user"`;
- подтверждённый email и занятый адрес ничего не записывают;
- сбой при записи в outbox откатывает и пользователя, и компанию;
- две транзакции читают адрес как свободный до того, как кто-то из них пишет; ограничение даёт закоммитить одной, другая получает `Email is taken`;
- если сохранение отслеживает ORM, нарушение всплывает на `flush()`, который `transaction()` делает перед коммитом, и это по-прежнему `IntegrityError`.

Фрагменты, которые статья показывает как части классов (агрегат, репозиторий поверх `_db`, `User` с событиями),
не запускаются в напечатанном виде; их полные версии для проверок на PostgreSQL лежат в `support.py`.
